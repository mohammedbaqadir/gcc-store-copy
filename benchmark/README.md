# Benchmark: one-shot prompt vs. saudi-store-copy skill

Same model, same 7 products, same underlying rules — one run as a single detailed prompt, one run through the skill.

**Model:** DeepSeek V4 Flash (identical for both runs)
**Input:** [`products.json`](./products.json) — 7 products, unchanged between runs
**One-shot prompt used:** [`one-shot-prompt.md`](./one-shot-prompt.md)

The one-shot prompt contains the same facts-only, no-fabrication, no-generic-filler rules as the skill — written out in full, one time, in the prompt itself. The point of this test isn't "does the skill know things the prompt doesn't" — it's what happens to output quality and consistency across a batch when those same rules exist as enforced process (skill) vs. as instructions the model has to hold onto unprompted for 7 items in a row (one-shot).

## What the data actually shows

Both runs stayed grounded in the supplied facts — no fabricated specs in either. That's expected: a detailed one-shot prompt can enforce factual grounding just as well as the skill can, for a single request. That was never really in question.

The difference is in what the copy is _for_. A product description is sales copy, not a data audit. The one-shot's `Missing info:` lines are useful during development, but they leak an internal QA step into the deliverable — no live store would ship "Missing info: age rating not specified" under a children's book listing. The skill never does this: it drops what it can't support and stays in the frame of a customer-facing pitch, on all 7 items, without exception.

The skill's output is also structurally consistent in a way the one-shot isn't: a hook line, a one-line context sentence, a scannable bullet list of reasons to buy, then price and caveats — the same shape on product 1 and product 7. The one-shot varies: some entries are plain paragraphs, some (Mug, AirPods) use bullets, none use a hook line. That inconsistency is normal for a single long prompt asked to hold many instructions across many items — nothing enforces the same structure item to item.

Neither run independently verifies specs against the real product (that's not the skill's job — it isn't a QA layer for source data, it's a copywriting layer that refuses to invent facts it wasn't given). Both are equally bound by whatever's in `products.json`.

**What this justifies:** not "the skill prevents hallucination better than a good prompt" — a good prompt does that too. What it justifies is consistent, sales-ready structure and tone across every item in a batch, without the operator having to rewrite or re-specify the rules each time, and without the internal QA process bleeding into what the customer sees. That's the same reason a style guide beats freehanding a description each time, even when a skilled writer could freehand something equally good once — the value is reliability at scale, not one-shot intelligence.
